### 2026-09-01 — Database: Supabase (Postgres + pgvector)
Already decided in `context.md`. User has an existing Supabase project to use directly (no local Postgres needed).

### 2026-09-01 — LLM synthesis: Grok (xAI) instead of Claude/Anthropic
**Why:** User is a student building this for free/low-cost; already has an xAI API key. Anthropic was the original plan in `context.md` but wasn't cheaper/free for this use case.
**Effect:** `backend/analysis/analyst.py` and `backend/report/assembler.py` use the `openai` Python SDK pointed at `https://api.x.ai/v1` (xAI's API is OpenAI-compatible) instead of the `anthropic` SDK. Model constant: `grok-4` — check console.x.ai for the current model name if this errors as unavailable.
**Superseded** by the next entry — switched to Groq instead.

### 2026-09-02 — LLM synthesis: Groq instead of Grok/xAI
**Why:** User decided to switch providers ("i am changing to groq"). Note this is a genuinely different company/API from xAI's "Grok" despite the near-identical name — easy to mix up.
**Effect:** `backend/analysis/analyst.py` and `backend/report/assembler.py` now point the `openai` SDK at `https://api.groq.com/openai/v1` (also OpenAI-compatible) with `GROQ_API_KEY`, not `XAI_API_KEY`. `.env`/`.env.example` updated accordingly.
**Model chosen:** `openai/gpt-oss-120b` — queried `client.models.list()` against the real account to see what's actually available (the first guess, `llama-3.3-70b-versatile`, 404'd — deprecated/unavailable). gpt-oss-120b is a large open-weight reasoning model, chosen for quality on structured-output tasks.
**Gotcha found by testing, not guessing:** gpt-oss-120b is a *reasoning* model — it spends tokens on hidden chain-of-thought before the final answer, so a low `max_tokens` (tried 50) silently truncates it to an empty response, which then fails JSON-mode validation with an opaque `json_validate_failed` error. Fixed by raising `max_tokens` (2048 in analyst.py, 1024 in assembler.py) and setting `extra_body={"reasoning_effort": "low"}` to keep the hidden-reasoning overhead small for this task.
**Verified:** ran a real end-to-end call through `generate_headline_and_summary()` with real signal data — got back a coherent headline and 4-sentence exec summary from the live API, not a mock.

### 2026-09-01 — Embeddings: local sentence-transformers instead of OpenAI
**Why:** Student wants zero ongoing API cost. OpenAI embeddings are cheap but not free and require a billed account; a local open-source embedding model has no per-call cost and no key to manage.
**Effect:** `backend/detection/change_detector.py` uses `sentence-transformers` (`all-MiniLM-L6-v2`, 384-dim) run locally instead of OpenAI's `text-embedding-3-small` (1536-dim). This changed the `embedding` column dimension in `backend/db/models.py` and `infra/sql/schema.sql` from `VECTOR(1536)` to `VECTOR(384)`. Tradeoff: MiniLM is a smaller, less accurate model than OpenAI's — the eval set in `/eval` is what tells us if it's good enough for this use case; revisit if precision is poor.
**Superseded:** the `OPENAI_API_KEY` env var and OpenAI embeddings call from the original scaffold — no OpenAI account needed at all now.

### 2026-09-02 — Local dev Python: 3.12, not the system default 3.14
**Why:** Python 3.14 is too new — several dependencies (`pydantic-core`, `greenlet`) are Rust/C extensions with no prebuilt wheels for 3.14 yet, and building them from source failed (`pyo3` doesn't support 3.14 yet either). Python 3.12 was already installed on the machine and has full wheel coverage for every dependency here.
**Effect:** the project venv (`backend/.venv`) is created with `py -3.12 -m venv .venv`, not the bare `python` on PATH. Anyone setting this up locally needs Python 3.12 available (check with `py -0`).

### 2026-09-02 — Postgres driver: psycopg (v3) instead of psycopg2-binary
**Why:** `psycopg2-binary` had no wheel at all for the Python version being tested (3.14) and pip fell back to compiling from source, which failed without `pg_config`/PostgreSQL headers installed. `psycopg` v3 is the actively maintained successor with much better wheel coverage across Python versions.
**Effect:** `backend/requirements.txt` uses `psycopg[binary]==3.2.10`. SQLAlchemy's `postgresql://` URL scheme defaults to psycopg2 when it's absent — since only psycopg3 is installed here, `DATABASE_URL` must use the `postgresql+psycopg://` scheme (Supabase gives you `postgresql://`; just add `+psycopg`).
**Resolved:** installs cleanly under Python 3.12; verified with `pip install -r backend/requirements.txt`.

### 2026-09-02 — PDF rendering: Playwright instead of WeasyPrint
**Why:** WeasyPrint requires the GTK/Pango/cairo native libraries, which aren't installed by default on Windows and are painful to set up (this is a well-known WeasyPrint-on-Windows pain point, confirmed by an actual `OSError: cannot load library 'libgobject-2.0-0'` when tested). Playwright's Chromium is already a dependency (used by the jobs collector for JS-rendered career pages), so reusing it for PDF export avoids adding a second, fragile native dependency.
**Effect:** `backend/report/pdf_renderer.py` renders the Jinja2 HTML template to a temp `.html` file, navigates Chromium to it with `page.goto()` (`page.set_content()` was tried first but doesn't reliably resolve local `file://` image sources — charts rendered as broken image icons), then calls `page.pdf()`. `weasyprint` removed from `backend/requirements.txt`.
**Verified:** ran a full smoke test with fake signal data — charts render correctly and the PDF layout, colors, and priority badges all look right (see `docs/06-report-assembly.md`).

### 2026-09-02 — Change-detection threshold recalibrated for local embeddings: 0.98, not 0.92
**Why:** The original 0.92 threshold was written for OpenAI's `text-embedding-3-small`. Local MiniLM (`all-MiniLM-L6-v2`) produces much more compressed cosine similarities — a *real*, meaningful content change (price + feature change) still scored 0.965 similarity, which the 0.92 threshold classified as noise (a false negative). Swept thresholds 0.92 → 0.98 against the 2-example placeholder eval set; 0.97+ correctly separates the one real-change example (0.965) from the one noise example (0.991).
**Effect:** `DEFAULT_SIMILARITY_THRESHOLD` in `backend/detection/change_detector.py` is now `0.98`.
**Caveat — not actually tuned yet:** this is calibrated on only 2 synthetic placeholder examples, not real data. Treat it as a starting point, not a trustworthy number. Must be re-tuned once real labeled snapshot pairs from actual competitor pages are added to `/eval/change_detection_eval_set.json`.

### 2026-09-03 — Competitors for the ComplyDo pilot: Vanta + Drata
**Why:** ComplyDo (Berlin, YC-backed, DORA/NIS2/ISO27001 GRC automation) needed 2-3 real competitors with real source URLs — this was the last open decision blocking real (non-synthetic) pipeline runs. Researched ComplyDo's actual market instead of guessing: Tracxn names Vanta directly as a competitor; Drata is the other major player in the same GRC-automation category. Both were checked for real, scrapable content across all four collector types before being picked — candidates considered and passed over: **Scytale** (EU-native NIS2-focused peer, good content but less recognizable) and **StartComply** (closest true peer in size/market but has no visible careers page, weakening the jobs collector). User confirmed Vanta + Drata via AskUserQuestion.
**Effect:** `backend/db/seed.py` (new) seeds `TargetCompany("ComplyDo")` with both competitors and 4 sources each:
- Vanta: pricing `vanta.com/pricing` (feature-tier/CTA page, no numeric prices), feature `vanta.com/whats-new` (dated monthly changelog), jobs `jobs.ashbyhq.com/vanta` (Ashby-hosted board), news `vanta.com/company/press` (no dates on entries — hash-only, not date-sortable).
- Drata: pricing `drata.com/pricing` (same feature-tier/CTA shape), feature `drata.com/blog` (no dedicated changelog exists, blog is the closest proxy — dated posts), jobs `drata.com/about/careers` (native to their own site, not an external ATS), news `drata.com/about/news` (dated press releases).
**Caveat:** neither pricing page shows numeric prices (both are "contact sales" + feature-tier matrices) — the pricing collector needs to hash/diff the *tier and feature-matrix content*, not dollar amounts. Run `python -m backend.db.seed` once `infra/sql/schema.sql` has been applied and `DATABASE_URL` is set.

### 2026-09-03 — First real collector run: schema applied, seeded, 3 bugs found and fixed
Applied `infra/sql/schema.sql` to the real Supabase project (tables existed empty from a prior session), ran `backend/db/seed.py`, then ran all collectors against the real Vanta/Drata URLs — exactly the "next real blocker" flagged in `docs/00-overview.md`. Found and fixed real issues synthetic data never surfaced:
1. **`NewsCollector`'s `url` field is a search query, not a URL** (it queries the HN Algolia API, see `backend/collectors/news_collector.py`) — `seed.py` was wrongly seeded with press-page URLs for the news source. Fixed to `"Vanta"` / `"Drata"` (query terms). This also broke the shared `is_allowed_by_robots()` robots check (tried to parse `"Vanta"` as a URL). Fixed by adding `BaseCollector._robots_check_url()`, overridden by `NewsCollector` to check the actual HN API host instead of `self.url`.
2. **`is_allowed_by_robots()` used `RobotFileParser.read()`, which sends Python's generic default `urllib` User-Agent** — Drata's bot protection (Cloudflare) 403s that generic UA even though the actual robots.txt (fetched with our real bot UA) explicitly allows `/pricing` and `/blog`. Worse: `RobotFileParser` **fails closed** (disallow-all) on a 401/403, and *also* defaults to disallow-all when never successfully parsed at all (confirmed by testing — a 404 robots.txt was being treated as fully disallowed, backwards from RFC 9309, which says a missing/unreachable robots.txt means no restrictions). Fixed in `backend/collectors/base.py`: fetch robots.txt ourselves with our real `USER_AGENT`, and explicitly set `parser.allow_all = True` on any non-200 or fetch failure.
3. **Drata's own careers page (`drata.com/about/careers`) is Cloudflare-bot-challenge-protected** — Playwright gets served a "Just a moment..." interstitial instead of real content, confirmed by inspecting the captured text directly. Not worth bypassing (would cross into bot-detection evasion, and there's no external ATS mirror — no Greenhouse/Lever/Ashby board found for Drata). **Decision (user-confirmed): drop the jobs source for Drata**, accept 3/4 source types for that competitor; Vanta keeps all 4 (its Ashby-hosted board works fine). A secondary reason this needed to go, not just be left broken: the Cloudflare interstitial embeds a unique `ray id` per request, so its content hash would differ on *every* fetch — it would have registered a false "change" signal on every single pipeline run forever, not just failed silently.
**Result:** all 7 remaining sources (Vanta: pricing/feature/jobs/news, Drata: pricing/feature/news) fetch real content successfully as of this session. `backend/db/seed.py` updated to match.

**Follow-up, same session — first full real pipeline run:** ran `run_pipeline_for_target()` end-to-end (not just collectors standalone) against the real DB. All 7 sources collected, embedded (local MiniLM), and stored as baseline snapshots; 0 signals (expected — first run has no prior snapshot to diff against); Groq's live API generated a real "no notable activity" headline/summary; PDF rendered successfully via Playwright with both charts. Verified DB row counts match exactly (7 sources → 7 snapshots, 1 report, 0 signals). This is the first time any part of this pipeline has run against real data end-to-end rather than synthetic/fake fixtures. A second run (after real content actually changes, or by hand-editing a stored snapshot to fake a change) is still needed to see a signal actually get detected, analyzed, scored, and rendered for real.

### 2026-09-03 — Frontend verified end-to-end; RLS gap and Next.js CVEs fixed
Ran the frontend for the first time (`npm install`, `npm run dev`) against the real Supabase report generated earlier this session, to confirm it actually works before pushing to GitHub. Found and fixed two real issues:
1. **No RLS policies existed on `reports`/`signals`.** Supabase enables Row Level Security by default on new tables; with RLS on and zero policies, the anon key doesn't get an error — it silently gets an empty result, which would have looked like "the frontend is broken" with no obvious cause. Confirmed via a direct REST call (`curl .../rest/v1/reports` with the anon key returned `[]` despite a real row existing) and via `pg_class`/`pg_policies` against the live DB. **Fix:** added `ALTER TABLE ... ENABLE ROW LEVEL SECURITY` + a public-read `CREATE POLICY ... FOR SELECT USING (true)` for both tables to `infra/sql/schema.sql`, and applied the same to the live Supabase project (user confirmed applying it live). Reasoned as safe: no sensitive data in these tables, single-user portfolio project, and all writes go through the pipeline's direct `DATABASE_URL` connection, not the anon key — so anon only ever needs `SELECT`.
2. **`next@15.1.4` had 2 high + 1 critical npm-audit vulnerabilities**, including a named CVE (CVE-2025-66478) — this predates the scaffold but was never checked. Bumped to `15.5.25` (latest stable 15.x, matches what `npm audit fix` itself proposed) via `frontend/package.json`, which cleared the critical/high-severity issues. One moderate/high pair remains from a `postcss` dependency bundled inside Next's own build toolchain — clearing it needs a Next 16 major upgrade, a real breaking-change decision left for later, not bundled into this fix.
**Verified:** loaded `/report/<real report id>` in an actual browser (via claude-in-chrome) after these fixes — headline, date range, and executive summary render correctly from the live Supabase data.
