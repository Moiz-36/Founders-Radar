### 2026-09-01 — LLM synthesis: Grok (xAI) instead of Claude/Anthropic
**Why:** User is a student building this for free/low-cost; already has an xAI API key. Anthropic was the original plan in `context.md` but wasn't cheaper/free for this use case.
**Effect:** `backend/analysis/analyst.py` and `backend/report/assembler.py` use the `openai` Python SDK pointed at `https://api.x.ai/v1` (xAI's API is OpenAI-compatible) instead of the `anthropic` SDK. ### 2026-09-02 — LLM synthesis: Groq instead of Grok/xAI
**Why:** User decided to switch providers ("i am changing to groq"). Note this is a genuinely different company/API from xAI's "Grok" despite the near-identical name — easy to mix up.
**Effect:** `backend/analysis/analyst.py` and `backend/report/assembler.py` now point the `openai` SDK at `https://api.groq.com/openai/v1` (also OpenAI-compatible) with `GROQ_API_KEY`, not `XAI_API_KEY`. `.env`/`.env.example` updated accordingly.
**Model chosen:** `openai/gpt-oss-120b` — queried `client.models.list()` against the real account to see what's actually available (the first guess, `llama-3.3-70b-versatile`, 404'd — deprecated/unavailable). gpt-oss-120b is a large open-weight reasoning model, chosen for quality on structured-output tasks.
**Gotcha found by testing, not guessing:** gpt-oss-120b is a *reasoning* model — it spends tokens on hidden chain-of-thought before the final answer, so a low `max_tokens` (tried 50) silently truncates it to an empty response, which then fails JSON-mode validation with an opaque `json_validate_failed` error. Fixed by raising `max_tokens` (2048 in analyst.py, 1024 in assembler.py) and setting `extra_body={"reasoning_effort": "low"}` to keep the hidden-reasoning overhead small for this task.
**Verified:** ran a real end-to-end call through `generate_headline_and_summary()` with real signal data — got back a coherent headline and 4-sentence exec summary from the live API, not a mock.

### 2026-09-01 — Embeddings: local sentence-transformers instead of OpenAI
**Why:** Student wants zero ongoing API cost. OpenAI embeddings are cheap but not free and require a billed account; a local open-source embedding model has no per-call cost and no key to manage.
**Effect:** `backend/detection/change_detector.py` uses `sentence-transformers` (`all-MiniLM-L6-v2`, 384-dim) run locally instead of OpenAI's `text-embedding-3-small` (1536-dim). This changed the `embedding` column dimension in `backend/db/models.py` and `infra/sql/schema.sql` from `VECTOR(1536)` to `VECTOR(384)`. Tradeoff: MiniLM is a smaller, less accurate model than OpenAI's — the eval set in `/eval` is what tells us if it's good enough for this use case; revisit if precision is poor.
**Superseded:** the `OPENAI_API_KEY` env var and OpenAI embeddings call from the original scaffold — no OpenAI account needed at all now.

### 2026-09-02 — Local dev Python: 3.12, not the system default 3.14
**Why:** Python 3.14 is too new — several dependencies (`pydantic-core`, `greenlet`) are Rust/C extensions with no prebuilt wheels for 3.14 yet, and building them from source failed (`pyo3` doesn't support 3.14 yet either). Python 3.12 was already installed on the machine and has full wheel coverage for every dependency here.
**Effect:** the project venv (`backend/.venv`) is created with `py -3.12 -m venv .venv`, not the bare `python` on PATH. Anyone setting this up locally needs Python 3.12 available (check with `py -0`).

### 2026-09-02 — Postgres driver: psycopg (v3) instead of psycopg2-binary
**Why:** `psycopg2-binary` had no wheel at all for the Python version being tested (3.14) and pip fell back to compiling from source, which failed without `pg_config`/PostgreSQL headers installed. `psycopg` v3 is the actively maintained successor with much better wheel coverage across Python versions.
**Effect:** `backend/requirements.txt` uses `psycopg[binary]==3.2.10`. SQLAlchemy's `postgresql://` URL scheme defaults to psycopg2 when it's absent — since only psycopg3 is installed here, `DATABASE_URL` must use the `postgresql+psycopg://` scheme (Supabase gives you `postgresql://`; just add `+psycopg`).
**Resolved:** installs cleanly under Python 3.12; verified with `pip install -r backend/requirements.txt`.

### 2026-09-02 — PDF rendering: Playwright instead of WeasyPrint
**Why:** WeasyPrint requires the GTK/Pango/cairo native libraries, which aren't installed by default on Windows and are painful to set up (this is a well-known WeasyPrint-on-Windows pain point, confirmed by an actual `OSError: cannot load library 'libgobject-2.0-0'` when tested). Playwright's Chromium is already a dependency (used by the jobs collector for JS-rendered career pages), so reusing it for PDF export avoids adding a second, fragile native dependency.
**Effect:** `backend/report/pdf_renderer.py` renders the Jinja2 HTML template to a temp `.html` file, navigates Chromium to it with `page.goto()` (`page.set_content()` was tried first but doesn't reliably resolve local `file://` image sources — charts rendered as broken image icons), then calls `page.pdf()`. `weasyprint` removed from `backend/requirements.txt`.
**Verified:** ran a full smoke test with fake signal data — charts render correctly and the PDF layout, colors, and priority badges all look right (see `docs/06-report-assembly.md`).

### 2026-09-02 — Change-detection threshold recalibrated for local embeddings: 0.98, not 0.92
**Why:** The original 0.92 threshold was written for OpenAI's `text-embedding-3-small`. Local MiniLM (`all-MiniLM-L6-v2`) produces much more compressed cosine similarities — a *real*, meaningful content change (price + feature change) still scored 0.965 similarity, which the 0.92 threshold classified as noise (a false negative). Swept thresholds 0.92 → 0.98 against the 2-example placeholder eval set; 0.97+ correctly separates the one real-change example (0.965) from the one noise example (0.991).
**Effect:** `DEFAULT_SIMILARITY_THRESHOLD` in `backend/detection/change_detector.py` is now `0.98`.
**Caveat — not actually tuned yet:** this is calibrated on only 2 synthetic placeholder examples, not real data. Treat it as a starting point, not a trustworthy number. Must be re-tuned once real labeled snapshot pairs from actual competitor pages are added to `/eval/change_detection_eval_set.json`.

### 2026-09-03 — First real collector run: schema applied, seeded, 3 bugs found and fixed
Applied `infra/sql/schema.sql` to the real Supabase project (tables existed empty from a prior session), ran `backend/db/seed.py`, then ran all collectors against the real Vanta/Drata URLs — exactly the "next real blocker" flagged in `docs/00-overview.md`. Found and fixed real issues synthetic data never surfaced:
1. **`NewsCollector`'s `url` field is a search query, not a URL** (it queries the HN Algolia API, see `backend/collectors/news_collector.py`) — `seed.py` was wrongly seeded with press-page URLs for the news source. Fixed to `"Vanta"` / `"Drata"` (query terms). This also broke the shared `is_allowed_by_robots()` robots check (tried to parse `"Vanta"` as a URL). Fixed by adding `BaseCollector._robots_check_url()`, overridden by `NewsCollector` to check the actual HN API host instead of `self.url`.
2. **`is_allowed_by_robots()` used `RobotFileParser.read()`, which sends Python's generic default `urllib` User-Agent** — Drata's bot protection (Cloudflare) 403s that generic UA even though the actual robots.txt (fetched with our real bot UA) explicitly allows `/pricing` and `/blog`. Worse: `RobotFileParser` **fails closed** (disallow-all) on a 401/403, and *also* defaults to disallow-all when never successfully parsed at all (confirmed by testing — a 404 robots.txt was being treated as fully disallowed, backwards from RFC 9309, which says a missing/unreachable robots.txt means no restrictions). Fixed in `backend/collectors/base.py`: fetch robots.txt ourselves with our real `USER_AGENT`, and explicitly set `parser.allow_all = True` on any non-200 or fetch failure.
3. **Drata's own careers page (`drata.com/about/careers`) is Cloudflare-bot-challenge-protected** — Playwright gets served a "Just a moment..." interstitial instead of real content, confirmed by inspecting the captured text directly. Not worth bypassing (would cross into bot-detection evasion, and there's no external ATS mirror — no Greenhouse/Lever/Ashby board found for Drata). **Decision (user-confirmed): drop the jobs source for Drata**, accept 3/4 source types for that competitor; Vanta keeps all 4 (its Ashby-hosted board works fine). A secondary reason this needed to go, not just be left broken: the Cloudflare interstitial embeds a unique `ray id` per request, so its content hash would differ on *every* fetch — it would have registered a false "change" signal on every single pipeline run forever, not just failed silently.
**Result:** all 7 remaining sources (Vanta: pricing/feature/jobs/news, Drata: pricing/feature/news) fetch real content successfully as of this session. `backend/db/seed.py` updated to match.

**Follow-up, same session — first full real pipeline run:** ran `run_pipeline_for_target()` end-to-end (not just collectors standalone) against the real DB. All 7 sources collected, embedded (local MiniLM), and stored as baseline snapshots; 0 signals (expected — first run has no prior snapshot to diff against); Groq's live API generated a real "no notable activity" headline/summary; PDF rendered successfully via Playwright with both charts. Verified DB row counts match exactly (7 sources → 7 snapshots, 1 report, 0 signals). This is the first time any part of this pipeline has run against real data end-to-end rather than synthetic/fake fixtures. A second run (after real content actually changes, or by hand-editing a stored snapshot to fake a change) is still needed to see a signal actually get detected, analyzed, scored, and rendered for real.

### 2026-09-03 — Frontend verified end-to-end; RLS gap and Next.js CVEs fixed
Ran the frontend for the first time (`npm install`, `npm run dev`) against the real Supabase report generated earlier this session, to confirm it actually works before pushing to GitHub. Found and fixed two real issues:
1. **No RLS policies existed on `reports`/`signals`.** Supabase enables Row Level Security by default on new tables; with RLS on and zero policies, the anon key doesn't get an error — it silently gets an empty result, which would have looked like "the frontend is broken" with no obvious cause. Confirmed via a direct REST call (`curl .../rest/v1/reports` with the anon key returned `[]` despite a real row existing) and via `pg_class`/`pg_policies` against the live DB. **Fix:** added `ALTER TABLE ... ENABLE ROW LEVEL SECURITY` + a public-read `CREATE POLICY ... FOR SELECT USING (true)` for both tables to `infra/sql/schema.sql`, and applied the same to the live Supabase project (user confirmed applying it live). Reasoned as safe: no sensitive data in these tables, single-user portfolio project, and all writes go through the pipeline's direct `DATABASE_URL` connection, not the anon key — so anon only ever needs `SELECT`.
2. **`next@15.1.4` had 2 high + 1 critical npm-audit vulnerabilities**, including a named CVE (CVE-2025-66478) — this predates the scaffold but was never checked. Bumped to `15.5.25` (latest stable 15.x, matches what `npm audit fix` itself proposed) via `frontend/package.json`, which cleared the critical/high-severity issues. One moderate/high pair remains from a `postcss` dependency bundled inside Next's own build toolchain — clearing it needs a Next 16 major upgrade, a real breaking-change decision left for later, not bundled into this fix.
**Verified:** loaded `/report/<real report id>` in an actual browser (via claude-in-chrome) after these fixes — headline, date range, and executive summary render correctly from the live Supabase data.

### 2026-09-05 — v2 Phase 1: Supabase Auth + owner-scoped RLS, replacing public-read
**Why:** `docs/09-v2-plan.md` (approved 2026-09-04) calls for any logged-in user to track their own companies, which the v1 schema can't support — `target_companies` had no owner and `reports`/`signals` were world-readable by design (single-user portfolio case, see the 2026-09-03 RLS-gap entry).

RLS enabled on `target_companies`/`competitors`/`sources` with `owner full access` policies scoped through the `target_company_id` → `owner_id` chain (competitors/sources policies join up to `target_companies` since they have no `owner_id` of their own). `reports`/`signals` deliberately **keep** the existing public-read policy — a report link stays shareable without an account. Added an owner-scoped read policy to `snapshots` too, which had RLS enabled by Supabase's default but zero policies (same silent-empty-result trap as the 2026-09-03 entry, caught this time before it shipped rather than after).
**Frontend:** `@supabase/ssr` added (`frontend/lib/supabase/client.ts` for Client Components, `server.ts` for Server Components/Route Handlers). `frontend/middleware.ts` gates `/dashboard`, `/company/*`, `/settings` behind a logged-in session, redirecting to `/login?next=<path>`. Calls `getUser()`, not `getSession()`, so the SSR client revalidates against Supabase rather than trusting a cookie that could be stale or forged.
**Caveat — not yet tested end-to-end:** no real signup → add-company → dashboard walkthrough has been run against this yet (unlike every other entry in this log, which has a "Verified" line). Needs a real pass before this ships or gets committed.

### 2026-09-05 — v2 Phase 1: per-company report cadence, not a hardcoded weekly cron
**Why:** A single shared weekly schedule (the v1 design) doesn't work once arbitrary users can each track companies on their own cadence — `docs/09-v2-plan.md`'s user workflow lets each company set its own interval.
**Effect:** `report_interval_days INTEGER DEFAULT 7` added to `target_companies` (default preserves the old weekly behavior for existing rows, i.e. the ComplyDo pilot). `_is_report_due()` in `backend/main.py` checks elapsed time since a company's latest `report.created_at` against its own `report_interval_days`. `run_pipeline_for_target()`'s report window (`week_start`/`week_end`) now defaults off that same interval instead of a fixed 7 days, so a company checked every 2 days gets a 2-day report window.
**Scheduler effect:** `infra/scheduler_config.yaml` changed from a single weekly Monday-8am job targeting one hardcoded `target_company_id` to a **daily** job (`founders-radar-daily`, `0 8 * * *`) with an empty body. The Cloud Function no longer requires a `target_company_id` — with none given it calls the new `run_pipeline_for_all_active_companies()`, which loops every company and lets `_is_report_due()` decide who actually runs that day. A `target_company_id` is still accepted for a manual/on-demand single-company trigger, bypassing the due check. See `infra/cloud_function/main.py`.
**Not yet deployed:** per `docs/08-infra-scheduling.md`, the Cloud Function/Scheduler setup remains scaffolded only — this changes the code and config files, not a live GCP job. Playwright/Chromium-in-Cloud-Functions is also still unresolved (same doc).

### 2026-09-05 — v2 Phase 1: per-source failure isolation + `status` field
**Why:** With multiple companies and competitors now possible, one source failing (robots.txt block, Cloudflare challenge — the exact failure hit with Drata's careers page on 2026-09-03) must not silently kill the whole company's report, and the user needs a way to *see* that a source is broken instead of only finding out from logs.
**Effect:** `status TEXT DEFAULT 'active' CHECK (status IN ('active','broken','needs_review'))` added to `sources`. `run_pipeline_for_target()` in `backend/main.py` now wraps each source's `_process_source()` call in its own try/except — a failure sets `source.status = "broken"` and logs, but the loop continues to the next source and the report still assembles from whatever succeeded. `needs_review` is reserved for Phase 2 discovery output the user hasn't confirmed yet (not set anywhere yet). Surfaced in `frontend/app/company/[id]/page.tsx` as a status badge per source.

### 2026-09-05 — v2 Phase 1: baseline signal instead of an empty first report
**Why:** `_process_source()` previously returned `[]` on a source's first-ever collection (nothing to diff against) — fine for the single ComplyDo pilot company seeded by hand, but a bad first impression for a new self-serve user: their first report would say "no notable activity" despite the pipeline having found real pricing/feature/jobs content it just can't describe as a *change* yet.
**Effect:** New `summarize_baseline()` in `backend/analysis/analyst.py` (separate system prompt from `analyze_change` — explicitly told not to describe a "change" since there's nothing to compare against, just to factually summarize what's currently there). `Signal.is_baseline` (new column, default `false`) marks these; `old_snapshot_id`/`similarity_score` are `None` for them. `backend/report/assembler.py`'s summary prompt now tags each signal `[BASELINE]` or `[CHANGE]` so the LLM frames an all-baseline report as an initial competitive snapshot rather than "nothing happened." Both the PDF template (`report.html.jinja`) and the web `SignalCard.tsx` render a "baseline" badge and swap the field label to "What we found" instead of "What changed" for these.
**Caveat — not yet tested:** no baseline signal has actually been generated against a live Groq call in this session; the analogous `analyze_change` prompt was verified for real on 2026-09-03, this one hasn't been.

### 2026-09-05 — v2 Phase 2: auto-discovery via Groq + Tavily, human-in-the-loop
**Why:** `docs/09-v2-plan.md` Phase 2 — replacing the manual "type every competitor URL by hand" flow (what `backend/db/seed.py` does for ComplyDo) with an assisted one, while keeping a human review step before anything is saved, per the plan's confirmed decision (a blind-automation failure mode was already hit once: the Cloudflare-blocked Drata careers page).
**Effect:** New `backend/discovery/` package: `search.py` wraps the Tavily Search API (`TAVILY_API_KEY`, free tier, 1,000 req/month, no card — chosen over Brave Search, which needs a card even on its free tier, per the plan's already-resolved decision); `competitor_finder.py` searches `"{company} competitors alternatives"` and asks Groq to pick 3-5 real competitors (excluding review/listicle sites) with a confidence rating; `source_finder.py` runs one search per source type (pricing/feature/job_posting — `news` is skipped since that source's `url` is an HN Algolia query term, not a page, per the 2026-09-03 entry) and asks Groq to pick the best URL per type or `null`. Pricing/feature searches are restricted to the competitor's own domain via Tavily's `include_domains` filter — an unrestricted search for e.g. "Coda pricing" gets dominated by third-party aggregators (vendr.com, roundup blogs) ranking above the real page, confirmed by hand while building this. `job_posting` is deliberately left unrestricted since it's often legitimately on an external ATS (Greenhouse/Lever/Ashby).
**Two new FastAPI routes** (`POST /discover/competitors`, `POST /discover/sources` in `backend/main.py`) expose this to the frontend; neither writes to the database — they only return candidates for `frontend/app/company/new/page.tsx` to prefill into an editable form the user must explicitly submit ("Start tracking") before `target_companies`/`competitors`/`sources` rows are created.
**Caveat — not yet tested:** no real Tavily/Groq discovery call has been run end-to-end in this session (unlike e.g. the 2026-09-03 real-collector-run entries); `TAVILY_API_KEY` needs a real account and key before this can be exercised at all.

### 2026-09-07 — Scheduler deploy target: Cloud Run container, not a plain Cloud Function
**Why:** Walking through `docs/08-infra-scheduling.md`'s deploy steps in detail (in prep for actually deploying) surfaced two real blockers in the existing scaffold, neither hypothetical:
1. `infra/cloud_function/main.py` does `from backend.main import ...`, but `gcloud functions deploy --source=infra/cloud_function` only ever uploads that exact directory — it can't see `backend/` one level up. `infra/cloud_function/requirements.txt`'s `-r ../../backend/requirements.txt` has the same problem: that relative path never resolves during Cloud Build.
2. The already-known Playwright/Chromium gap (flagged since the original scaffold, see `docs/08-infra-scheduling.md`'s prior "Gotchas") — GCP's default Cloud Functions Python runtime has no Chromium and Cloud Functions doesn't support installing custom system packages at all, so there was never a version of `gcloud functions deploy` that could have worked here.
**Effect:** New `infra/cloud_function/Dockerfile`, based on `mcr.microsoft.com/playwright/python:v1.49.0-jammy` (Chromium + its system deps preinstalled), **built from the repo root as context** — not from `infra/cloud_function/` — so it can `COPY backend/` alongside `infra/cloud_function/main.py`, solving both blockers at once: the import now resolves because `backend/` is genuinely present in the image, and `requirements.txt` no longer needs a relative path since the Dockerfile installs `backend/requirements.txt` directly by its real path. Re-runs `playwright install --with-deps chromium` during the build so the browser build matches the exact `playwright==1.49.1` pin in `backend/requirements.txt`, rather than trusting the base image's bundled version to be close enough. New root `.dockerignore` keeps the build context from uploading `frontend/` (node_modules), venvs, and generated `backend/output/` files.
**Deploy target changed from Cloud Functions to Cloud Run** as a consequence — Cloud Run is what actually supports a custom container image; Cloud Functions (1st or 2nd gen) only supports Google's buildpacks, not an arbitrary Dockerfile. The function code itself (`run_weekly_pipeline` in `main.py`) is unchanged — `functions-framework` serves the same entrypoint identically whether it's a raw Cloud Function or containerized on Cloud Run (Google's own documented pattern, not a workaround). `infra/scheduler_config.yaml`'s deploy comment block and `docs/08-infra-scheduling.md` updated to the `gcloud builds submit` → `gcloud run deploy --no-allow-unauthenticated` → OIDC-authenticated Scheduler job sequence. Deliberately **not** `--allow-unauthenticated`: every invocation triggers real Groq/Tavily calls and DB writes, so only Cloud Scheduler's own service account (via `--oidc-service-account-email`) should be able to call it.
**Not yet deployed or tested:** no GCP project exists yet for this to run against — this fixes the deploy *mechanics* (the Dockerfile builds correctly given a project), not a verified live deployment. The `mcr.microsoft.com/playwright/python:v1.49.0-jammy` tag should be spot-checked against whatever `playwright` version `backend/requirements.txt` pins at deploy time, in case it's moved past 1.49.1 by then.

### 2026-09-08 — Fixed a broken build command: `gcloud builds submit --tag ... -f <path>` doesn't exist
**Why:** Actually attempting the deploy (real GCP project, real `gcloud` CLI) hit `ERROR: (gcloud.builds.submit) unrecognized arguments: -f` — the build command documented in the 2026-09-07 entry above and written into `infra/scheduler_config.yaml`'s comment block was never actually valid. Confirmed via `gcloud builds submit --help`: `--tag` always runs a plain `docker build -t $TAG .` against a Dockerfile at the **source root**, with no flag to point it elsewhere. Since `infra/cloud_function/Dockerfile` intentionally lives one level down from the repo root (so it can `COPY backend/`, per the 2026-09-07 entry), the `--tag` shorthand was never going to work here — this wasn't a typo, the command shape itself is incompatible with a non-root Dockerfile.

**Real gap found while prepping this: the backend's interactive API was never actually deployed anywhere.** The live GCP Cloud Run service only ever ran `infra/cloud_function/main.py`'s `run_weekly_pipeline` — a thin wrapper around the *scheduled* multi-company run, deployed `--no-allow-unauthenticated` (only Cloud Scheduler's own service account can invoke it). `backend/main.py`'s actual FastAPI app — `/discover/*`, `/chat/*`, `/run/{id}`, the endpoints the frontend's `PIPELINE_API_BASE_URL` calls for real-time features — was never deployed publicly at all; every use of those endpoints this whole project (including this session's QA pass) was against a local `uvicorn` instance. This had gone unnoticed because Supabase-backed features (auth, dashboard reads) don't need the backend at all.

**Security gap this surfaces, and the fix.** Every one of those FastAPI routes has "no auth of its own" by design — ownership/session checks live in the Next.js proxy routes (`frontend/app/api/*/route.ts`) in front of them, which was a safe assumption only because GCP's Cloud Run IAM made the backend unreachable by anyone else. Render web services are public by default, so deploying the same app there as-is would let a stranger who finds the URL hit `/run/{id}` or `/discover/*` directly and burn real Groq/Tavily quota for free. Fixed with a new shared-secret check: `backend/main.py` gained a `require_shared_secret` middleware (no-op when `PIPELINE_SHARED_SECRET` is unset, so local dev is unaffected) checking an `x-pipeline-secret` header on every route except `/health`; all four Next.js proxy routes now send it via a small shared helper, `frontend/lib/pipelineFetch.ts`. Documented in both `.env.example` and `frontend/.env.local.example`.

**New deploy artifacts.** `infra/render/Dockerfile` (repo-root build context, same Playwright/Chromium base image as `infra/cloud_function/Dockerfile`, but running `uvicorn backend.main:app` directly instead of the GCP-specific function wrapper — this is the piece that was actually missing) and a `render.yaml` Blueprint at the repo root defining both a web service (the FastAPI app) and a cron job (`backend/cron_run_all.py`, the Render equivalent of Cloud Scheduler's daily trigger — `run_pipeline_for_all_active_companies()` already decides per-company due-ness internally, same as the GCP path).
